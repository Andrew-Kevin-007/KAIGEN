- 2026-11-03 step 1a (derivation read from lib.rs, not from the docs) | per token T, every window (a, a+24h]: sends <= C (window log: used(now-24h, now] + amount <= C, fold only moves a send later, so it can only over-count); queue part, delay D >= 24h: every request executed in the window has r <= x-D <= a < x, so all of them sit in the queue together at instant a and the queue sum is <= P (fits_pending on request AND on the failed-execute re-queue), hence loss <= C + P; D < 24h: requests made inside the window are bounded by the 24 h request budget (<= P) on top of the ones queued at a, hence C + 2P. Consequences I will verify by mutation instead of trusting: the 24 h request budget and queue expiry are NOT load-bearing for the D >= 24h bound (they matter for D < 24h and for stale items); the per-key share/slots do not enter the account-wide bound at all (they are an attribution/availability property: key k asks for <= P/n in any 24 h); strikes add nothing. Two code facts to pin: (1) no method assigns delay_secs after init, so the floor holds for the vault's life in a production build; (2) `on_send_done` refunds by heuristic (exact (ts, amount) match, else first entry with t >= ts and a >= amount): sound for a callback inside 24 h (the credit can only move to a later slot, i.e. over-count), unsound for a failure callback arriving more than 24 h late (the entry may have been pruned and another send's entry is reduced): an assumption (receipts resolve in seconds), not a code guard.
